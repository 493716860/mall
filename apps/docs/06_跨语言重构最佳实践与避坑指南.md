# 跨语言重构最佳实践与避坑指南

将 Java/Spring Boot 版 **芋道 Mall** 重构为其他语言（如 **Go (Gin / GORM)**, **Node.js (NestJS)**, **Python (FastAPI)**, **Rust (Axum)**）时，需严格遵循以下 6 大避坑法则：

---

## ⚠️ 1. 金额单位与精度防护 (必须统一为【分】)

* **避坑点**：Java 源码中所有价格字段（商品价格 `price`、运费 `delivery_price`、优惠金额 `discount_price`、订单实付 `pay_price`）在数据库中均为整型 `int / bigint`，单位是 **分**。
* **重构要求**：
  * 切勿在后端将金额声明为 `float` 或 `double` 类型，避免浮点数精度丢失问题。
  * 前端展示时除以 100 转换成元，但在后端计算、数据库读写、微信支付 API 交互时，**一律维持 integer (分)**。

---

## ⚡ 2. 高并发防超卖：原子扣减库存 (Atomic Stock Reduction)

* **避坑点**：不能先 `SELECT stock` 读取库存，在内存中判断 `stock >= count` 再执行 `UPDATE stock = stock - count`。在高并发场景下会导致严重的超卖！
* **重构要求**：
  * 必须使用带有条件检查的原子更新语句：
    ```sql
    UPDATE product_sku 
    SET stock = stock - ?, sales_count = sales_count + ? 
    WHERE id = ? AND stock >= ?;
    ```
  * 在 ORM (如 GORM) 中必须检查 Influenced Rows（受影响行数）。如果受影响行数为 0，说明库存不足，应直接提示并回滚事务。

---

## 🔐 3. JWT Token 解析与租户/用户上下文提取

* **避坑点**：芋道后端在 Header 中传输 JWT Token，格式为 `Authorization: Bearer <token>`。
* **重构要求**：
  * 必须配置 HTTP Middleware 统一拦截拦截 `/app-api/*` 和 `/admin-api/*` 路由。
  * 从 Header 解析出的 `user_id` 或 `admin_id` 应绑定到当前 Request Context 中（例如 Go 的 `c.Set("userId", userId)`）。
  * 无论后台还是小程序，接口内读取当前操作人 ID 一律从 Context 取，严禁依赖前端 Body 传来的 `userId`。

---

## 🔄 4. 订单状态机 (Order Status Machine) 严密迁移

订单状态流转必须保持强一致性：

```text
[0: 待付款] ---> 支付成功 ---> [10: 待发货]
     |                              |
     |---- 取消订单/超时关闭 ---->   |---- 商家发货 ----> [20: 待收货]
     v                              |                         |
[40: 已取消]                         |-- 申请退款 --           v
                                    v             |      [30: 已完成]
                                [50: 售后中] <-----
```

* 严禁跳过中间状态更新。每一次状态变更必须记录 `trade_order_log` 日志。

---

## 🕒 5. 时间格式与时区处理 (ISO-8601 / RFC3339)

* **避坑点**：Java 标准的时间返回格式为 `"yyyy-MM-dd HH:mm:ss"`。
* **重构要求**：
  * 在 JSON 序列化时，Go / Node.js 默认可能返回带 T 和 Z 的 UTC 格式（如 `"2026-10-14T07:30:00Z"`）。
  * 为了与原 `miniapp` 和 `admin` 前端解析代码 100% 兼容，必须在全局 JSON 序列化器中将时间格式化为 `"2026-10-14 07:30:00"`。

---

## 🛡️ 6. 逻辑删除 `deleted` 标志处理

* 原 Java 项目中所有表均包含 `deleted` 字段（`bit(1)` 或 `tinyint`，`0` 表示未删除，`1` 表示已删除）。
* 无论使用何种 ORM，所有 `SELECT` 查询必须自动附加 `WHERE deleted = 0` 过滤条件；所有 `DELETE` 操作必须转换为 `UPDATE table SET deleted = 1` 软删除。
